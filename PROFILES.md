# n3 Profile and Authorship Contract

This document defines the privacy and identity boundary for M8 before profile schema, APIs, or views are added. Implementations must preserve these rules unless a later migration explicitly changes the contract.

## Core invariants

- A viewer must never learn the existence, title, count, URL, tags, dates, avatar, profile metadata, or plugin output of a profile or page they cannot access.
- Authorization happens before projection, counting, grouping, pagination, and plugin contribution. Fetching everything and redacting rows afterward is not acceptable.
- Denied and nonexistent profile routes both return `404`; profile routes must not expose an account-enumeration distinction.
- Administrator status does not grant implicit access to another user's private profile or pages.
- Existing editor authorization remains unchanged. Profile work may add viewer-filtered queries to `AccessService`, but must not broaden `canViewPage()`, `canEditPage()`, or ownership rules.

## Identity fields

The three identity values have different purposes:

| Value | Purpose | Mutability | Visibility |
| --- | --- | --- | --- |
| `username` | Local login identifier | Mutable after current-password confirmation | Returned only in an authorized profile/account projection |
| `display_name` | Human-readable author name | Mutable | Returned only when the viewer may see the profile identity |
| `profile_slug` | Stable URL identifier | Immutable after assignment | Present only in authorized profile links and public-profile responses |

`profile_slug` is generated by the server, never accepted as an arbitrary profile-settings value, and stored lowercase with the shape `[a-z0-9]+(?:-[a-z0-9]+)*`. Existing users receive a deterministic slug based on their current username plus user ID, with `user-{id}` as the fallback. New users receive a slug when their account is created. The user ID suffix makes collision handling deterministic.

Changing `username` or `display_name` must not update `profile_slug`. No username-based alias or redirect is created. Profile slugs are unique case-insensitively and are not reused while their user record exists.

`display_name` falls back to the current username only inside an authorized identity projection. Biography and avatar reference are profile metadata, not authentication data. New and migrated profiles default to `private` visibility.

## Canonical profile route

The canonical HTML route is:

```text
GET /u/{profile-slug}
```

- The stored lowercase slug is the only canonical URL.
- A missing, malformed, or unauthorized slug returns the same generic `404` response.
- A self or signed-in-only response uses `no-store` and `noindex`.
- A public-profile response may use a canonical link and normal public caching/indexing rules, but it contains only the anonymous projection defined below.
- Profile API and avatar endpoints added later must apply the same viewer decision independently; possession of a URL is never authorization.

`ROUTES.md` inventories the implemented profile route alongside its access, caching, indexing, and response contract.

## Profile visibility

`profile_visibility` has exactly three values:

| Value | Self | Other signed-in user | Anonymous viewer |
| --- | --- | --- | --- |
| `private` | Full self projection | `404` | `404` |
| `members` | Full self projection | Signed-in projection | `404` |
| `public` | Full self projection | Signed-in projection | Public projection |

The projections are:

- **Self:** display name, username, biography, avatar, visibility setting, profile URL, and the three page groups defined below.
- **Signed-in:** authorized display identity, biography, avatar, profile URL, and only pages the viewer may open through the profile-aware `AccessService` filter. Credential and account-administration fields are never included.
- **Public:** display name, username, biography, avatar, profile URL, and only active published pages authored by this profile. Enabling `public` is an explicit opt-in to expose these identity fields anonymously.

Changing visibility takes effect on the next request. It must not alter resource shares, page publication state, authorship, or page URLs.

## Avatar visibility

An avatar is part of the profile identity projection:

- The profile owner can always retrieve their own avatar.
- Another signed-in user can retrieve it only when that user may view the profile.
- An anonymous user can retrieve it only for a `public` profile.
- A page-information view may retrieve the author's avatar only when that viewer may see the author's profile identity.
- Otherwise the UI uses the generic avatar treatment without requesting or revealing the stored avatar reference.

Avatar files must later be served through an authorization-aware route using an opaque server-side reference. Database values, filesystem paths, original filenames, and direct static URLs are never exposed. Unauthorized and absent avatars both return `404`.

## Authorship semantics

`author_id` records who created the page and does not change when the page is renamed, moved, edited, published, restored, or shared. `last_editor_id` records the most recent actor responsible for a meaningful page mutation.

| Event | `author_id` | `last_editor_id` | `first_published_at` |
| --- | --- | --- | --- |
| Create page/folder | Current actor | Current actor | `NULL` |
| Duplicate page | Duplicating actor | Duplicating actor | `NULL` even when the source is public |
| Edit title/content/tags/references or location | Unchanged | Current actor | Unchanged |
| First private-to-public transition | Unchanged | Current actor | Set once to current UTC time |
| Later unpublish or republish | Unchanged | Current actor | Retained unchanged |
| Restore a revision or trashed page | Unchanged | Current actor | Unchanged |
| Favorite-only preference change | Unchanged | Unchanged | Unchanged |
| Permanent deletion | Row removed | Row removed | Row removed |

Plugins and internal jobs may not submit arbitrary author IDs. A trusted plugin mutation uses the authenticated request actor supplied by core n3. Folder rows retain authorship for hierarchy integrity, but profile page lists and Page information include only `kind = 'page'`.

Deleting a user sets page author/editor references to `NULL` rather than deleting content. The page remains governed by its space and sharing rules.

## Author presentation and fallbacks

Page information resolves an author in this order:

1. If the viewer may see the author's profile identity, show `display_name`, falling back to the current username; include the authorized avatar and `/u/{profile-slug}` link.
2. If the author exists but their profile identity is hidden from this viewer, show **Private author** with a generic avatar and no profile link, username, slug, or avatar request.
3. If `author_id` is `NULL` or the account no longer exists, show **Unknown author** with a generic avatar and no link.

Public page publication does not automatically make its author's profile public. A published page whose author is private therefore uses the non-linking **Private author** fallback.

## Exact page-list filtering

All groups exclude deleted rows and folders. Page counts are computed after these filters. Inaccessible pages contribute nothing—not even a count.

### Self profile

The self view exposes three deliberate lenses:

- **Owned:** active pages whose `spaces.owner_id` is the current user. This includes pages created by collaborators inside the user's spaces.
- **Shared with me:** active pages returned by `AccessService::accessiblePageIds(false)` whose space owner is not the current user. Existing inherited space grants and shared-page-subtree rules apply unchanged.
- **Published:** active pages whose `author_id` is the current user and `is_public = 1`.

Published is a status/authorship lens and may repeat a page already present under Owned or Shared with me. The UI must make that overlap clear rather than changing authorization to force mutually exclusive groups.

### Another signed-in viewer

The candidate set is active pages with `author_id` equal to the profile owner. A profile-aware method on `AccessService` must return only candidates for which either:

1. the current user already has private viewer access through ownership, a space grant, or an inherited page-subtree grant; or
2. the page is currently public.

This is a dedicated profile-list decision; it does not make a public page editable or expose other private pages from the same space. The repository receives the authorized ID set from `AccessService` and must not reproduce sharing SQL independently.

### Anonymous viewer

Anonymous listing is allowed only when the profile is `public`. It contains active rows satisfying all of:

```text
kind = 'page'
is_deleted = 0
is_public = 1
author_id = profile owner
```

The anonymous query uses the public read side and never instantiates an authenticated access context. It does not include privately accessible, shared, merely owned, or unlisted ancestor pages.

## List response boundary

An authorized list item may contain only the page ID needed by the authenticated client, canonical page/public URL appropriate to that viewer, title, publication state, and sanitized display dates required by the profile UI. Tags, excerpts, references, collaborators, space details, and plugin data are excluded unless a later task explicitly adds each field behind the same authorization filter.

Sort all profile page lists by `updated_at DESC, id DESC` for stable ordering. Pagination and totals must operate on the filtered query, not an unfiltered intermediate set.

## Migration 003 implementation

`003_add_profiles_and_authorship.php` establishes the storage portion of this contract:

- Add profile display name, biography, stable unique slug, visibility, and opaque avatar reference to users.
- Add nullable `author_id` and `last_editor_id` foreign keys using `ON DELETE SET NULL`, plus nullable `first_published_at`, to pages.
- Backfill each existing user's display name from username, deterministic profile slug, `private` visibility, and no avatar.
- Backfill page author and last editor from the containing space owner without changing any share or publication row.
- For an existing public page, use its current `updated_at` as the documented legacy estimate of first publication; leave private pages `NULL`.
- When a first owner is created after a clean pre-setup installation, claim any still-unassigned seeded pages together with the existing space-owner assignment.
- Leave author/editor references nullable when no deterministic user exists; the UI then uses **Unknown author**.

The migration follows `MIGRATIONS.md`, preserves existing page/public slugs and timestamps, and adds no profile routes or public data exposure by itself.

## Repository and service implementation

`ProfileService` now enforces profile visibility before returning identity metadata, requires an `AccessService` context for every signed-in view, exposes only avatar availability rather than its opaque storage reference, and derives every group count from the filtered result. `ProfileRepository` owns the corresponding self, signed-in, and anonymous page projections and never returns deleted rows or folders.

Page, tag, reference, revision-restore, tree-move, deletion, and trash-restore writes now receive the authenticated actor explicitly from the route/service boundary. Creation and duplication establish authorship, meaningful writes update `last_editor_id`, favorite-only changes do not, and the first private-to-public transition uses a write-once `first_published_at` update.

## Avatar service implementation

`ProfileAvatarService` stores avatars separately under `data/avatars` and never returns their opaque database reference to a client. It accepts only server-detected JPEG, PNG, GIF, or WebP files up to 5 MB, with each dimension at most 4096 pixels and no more than 16,777,216 total pixels. Complete container validation rejects truncated files, MIME mismatches, trailing executable payloads, SVG, and other unsupported formats; client filenames, extensions, MIME declarations, and paths are ignored.

New files receive a randomized 40-hex-character basename and a server-selected extension. Database replacement uses the previously observed reference as a compare-and-swap guard; a failed or concurrent update removes the staged file while preserving the existing avatar. Successful replacement and deletion clear the old reference before making its file inaccessible. Delivery lookup uses the stable profile slug and the same self/members/public visibility rules as the profile projection, returning the same empty result for missing and unauthorized avatars.

Backup manifests now checksum only avatar files referenced by the SQLite snapshot. Restore validates the manifest against those database references before installing the database and avatar files. Older archives without profile metadata remain compatible because their avatar set is empty.

## Self-service profile implementation

Authenticated users can load and update their own approved profile projection through `/api/profile`, and upload or remove their avatar through `/api/profile/avatar`. The response contains safe `/u/{profile-slug}` and `/avatar/{profile-slug}` URLs but never the stored avatar reference. Display-name, biography, and visibility changes do not require a password or rotate sessions. Username changes require the current password, increment the session version, rotate the current session and CSRF token, and leave `profile_slug` unchanged.

`GET` and `HEAD` requests to `/avatar/{profile-slug}` independently enforce the current self/members/public visibility decision and return the same `404` for absent and unauthorized files. Avatar responses use `no-store`, and public avatar delivery remains independent of plugin boot. The responsive Profile & Account panel provides a live, safely rendered preview, avatar lifecycle controls, the stable profile URL, and the existing separate password/session controls.

## Profile page implementation

`GET /u/{profile-slug}` renders the same authorized projection enforced by `ProfileService`. Owners receive separate Owned pages, Shared with me, and Published by me groups with private editor links. Another signed-in user receives only authored pages that are public or included by the profile-aware `AccessService` decision; pages they can edit use the editor route while public-only results use the read-only public route. Anonymous visitors receive only active published pages authored by a profile that explicitly opted into `public` visibility, and that projection omits internal page IDs.

Signed-in profile responses use `no-store` plus HTTP and HTML `noindex` directives. Anonymous public profiles use canonical and Open Graph metadata with revalidation caching. Missing, malformed, and visibility-denied routes share the same generic `404` body and reveal no profile or page metadata. Anonymous profile routing and avatar delivery remain independent of plugin boot. Signed-in profile pages boot enabled plugins only after authentication so declared structured profile contributions can be resolved.

## Page information implementation

`PageInformationService` projects page provenance only after the surrounding page route has authorized the viewer. Its response contains a display-ready author state, word count, and validated created, first-published, and updated timestamps; it never returns an author ID, username, profile visibility, or avatar storage reference. The authenticated page API uses this projection to render a live Page information panel after References and Similar pages, and private previews and public articles render the same projection through `PageInformationView`.

The page author receives their own permitted profile/avatar links. Another signed-in viewer receives those links only for a members or public profile, and an anonymous viewer only for a public profile. Existing hidden identities render **Private author**; null or deleted author records render **Unknown author**. Both fallbacks use a generic avatar and contain no profile or avatar request. Public page publication alone never changes this identity decision. Word counts update while editing, valid first-publication dates appear only when present, and the responsive panel uses semantic definition lists and `time` elements.

## Page response boundary

`PageProjectionService` is the client-response allowlist for page details. The authenticated projection includes only the page fields required by the editor, already authorized tags/references/related pages and access flags, canonical UTC created/updated values, and the nested `PageInformationService` projection. Repository-only fields such as `author_id`, `last_editor_id`, deletion state, arbitrary joined account fields, and collaborator records are never copied into the response. Author login usernames are used only as the internal display-name fallback and are not serialized as a separate field.

The public controller passes templates only the published page title/slug and anonymous Page information projection after it has finished sanitizing content and loading public discovery data. Its directory query returns only published pages and the ancestor rows required to reach them. A private page used solely as a structural ancestor retains only its traversal identifiers and has a `NULL` title and slug before reaching the view; unrelated private and deleted rows are not queried into the directory projection. All exposed provenance timestamps are normalized to `YYYY-MM-DDTHH:MM:SSZ`, and invalid values become `NULL`.

## Plugin contribution boundary

Trusted plugins may extend signed-in profiles with structured tools/cards and authenticated Page information with structured rows. Each used slot must be explicitly listed in the manifest `contributions` array before the bootstrap can register its handler. Contribution text is bounded and escaped by core; optional links are accepted only inside the contributing plugin's own authenticated API namespace. Plugins cannot inject arbitrary HTML or core-resource URLs through these slots.

`PluginContributionService` builds a fresh allowlisted context only after the core profile or page authorization decision. Profile context contains the permitted display identity, authorized profile/avatar URLs, audience, self flag, visibility, and already-filtered group counts—never login usernames, biographies, IDs, storage references, or page records. Page context contains the permitted title/editor URL, publication/access flags, and the existing viewer-scoped Page information projection—never page content, raw IDs, collaborators, or repository fields.

One throwing contribution handler omits only that handler's output and records a log message containing the plugin ID and slot, without exception text or context. Bootstrap failures remain atomic, and disabled, invalid, failed, or undeclared plugins contribute nothing. All currently supported slots are authenticated-only: anonymous profiles and public articles do not boot plugin PHP or contain plugin contribution fields.

## Required authorization tests

The automated repository, service, migration/upgrade, API/security, backup, plugin-lifecycle, accessibility, and browser suites now prove at minimum:

- username and display-name changes do not change the profile slug;
- private profiles are indistinguishable from missing profiles to other viewers;
- member profiles are unavailable anonymously;
- public profiles expose only authored, active, published pages anonymously;
- signed-in profile lists include public or `AccessService`-authorized authored pages and nothing else;
- self Owned, Shared with me, and Published groups follow the exact definitions above;
- counts, empty states, pagination, avatars, and plugin slots do not leak filtered resources;
- hidden and deleted authors use the correct non-linking fallback;
- changing profile visibility does not modify sharing or publication;
- authorship, last-editor, and first-publication rules survive migration, backup, and restore.

`tests/profile_upgrade_compatibility.php` builds a schema-2 archive and drives it through the reusable production restore/startup verifier, proving the migration-003 backfill independently of the direct migration unit test. Container smoke coverage checks profile and avatar CSRF ordering, viewer-specific profile/page-information responses, and indistinguishable hidden resources. The browser matrix exercises password-confirmed username rotation on an isolated collaborator, stable profile URLs, avatar lifecycle, signed-in shared-page filtering, public/self rendering, responsive behavior, plugin capability presentation, and Axe WCAG A/AA scans of the settings dialog and signed-in/public profile pages.
